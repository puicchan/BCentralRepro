Data Storage & External Services

The application writes ingested records to three staging tables in a Microsoft SQL Server database (ZavaBankCore): StagingCheckImage, StagingWireConfirmation, and StagingRegulatoryFeed. All SQL is executed via raw JDBC PreparedStatement calls — no ORM is used. After each file is processed (successfully or with failure), a JSON event is published to a RabbitMQ topic exchange (zava.events) using the file.ingested routing key, allowing downstream consumers to react to ingestion outcomes.

Key Architectural Decisions

  • Poll-based file watching: The service runs a tight loop (default 5 s interval) scanning a shared directory rather than using filesystem change events, making it portable across container runtimes.
  • Per-file connection per insert: JDBC connections and RabbitMQ connections are opened and closed for every individual database insert and every event publish, rather than pooled — simple but creates high connection churn under load.
  • File-name-driven routing: File type detection is based on filename patterns (keywords + extensions), with a fallback keyword map, keeping routing logic entirely self-contained in Main.java.

Communication Patterns

Synchronous — File System (inbound)

The service polls a watch directory (default /shared/file-ingestion) at a configurable interval (default 5 000 ms) using java.io.File.listFiles(). File routing is determined by filename pattern matching (keyword + extension rules). There is no filesystem change-event mechanism; polling is blocking and sequential within each cycle.

Synchronous — JDBC / SQL Server (outbound)

Each parsed record triggers an executeInsert() call that opens a fresh DriverManager.getConnection(), executes a single PreparedStatement, and immediately closes both. There is no connection pooling, no transaction management across multiple inserts, no retry policy, and no circuit breaker. A failure to insert is logged and causes the file to be moved to the error directory.

Asynchronous — AMQP / RabbitMQ (outbound)

After each file is fully processed (or fails), a single AMQP publish is made to the zava.events topic exchange with routing key file.ingested. Each publish creates a new Connection and Channel from scratch. There is no retry policy, no dead-letter queue configuration, and no acknowledgement mechanism — if the publish fails, the error is only logged. The service does not consume any queues.

Resilience patterns: None. There are no circuit breakers (Resilience4j, Hystrix), no retry decorators, no timeout configuration, and no bulkhead patterns applied to either JDBC or AMQP calls.

Service discovery: None. SQL Server and RabbitMQ hostnames are hardcoded in fileingestion.properties and can be overridden at runtime via environment variables (SQLSERVER_URL, RABBITMQ_HOST). There is no Eureka, Consul, or Kubernetes DNS-based service discovery.

API gateway: None applicable — the service has no HTTP interface.

Security posture: No authentication, no TLS, and no authorization checks are implemented. RabbitMQ credentials are configured as plaintext in the properties file (defaulting to guest/guest). The JDBC connection string has encrypt=false;trustServerCertificate=true, explicitly disabling TLS for the SQL Server connection. All service communications are unauthenticated and unencrypted by default.

Primary Workflows

Workflow 1: File Ingestion Polling Cycle

Entry point: The application's main loop, which runs continuously on a configurable interval (default 5 000 ms).

Steps:

  1. Scan watch directory — The service lists all files in the configured watch path (/shared/file-ingestion). Files already moved to processed or error subdirectories are excluded from scanning.
  2. Classify file type — For each regular file, the filename is matched against keyword-and-extension rules to determine its type. Files matching check.csv become check_images; files matching wire.txt become wire_confirmations; files matching (reg|feed).(csv|txt) become regulatory_feeds. Unrecognized files are silently skipped.
  3. Parse file content — The file is read line-by-line using the format appropriate for its type (CSV split for check images and regulatory feeds; fixed-width byte offsets for wire confirmations).
  4. Persist records — Each parsed record is written as an INSERT to the corresponding SQL Server staging table. A failed insert is caught, logged, and causes the file to be treated as failed overall.
  5. Publish ingestion event — Regardless of success or failure, a JSON event is published to RabbitMQ with the file name, file type, and outcome status (processed or failed).
  6. Move file — Successfully processed files are moved to the processed directory; failed files are moved to the error directory. The file is no longer visible in the watch directory after this step.

Workflow 2: Check Image File Processing

Entry point: A file matching check.csv detected in the watch directory.

Steps:

  1. Read the first line only of the CSV file (check image records are expected to be single-line).
  2. Split the line by comma into fields: CheckNumber (field 0), AccountNumber (field 1), ImagePath (field 2).
  3. If the file is empty or the line cannot be parsed, the file is marked as failed.
  4. Execute a single INSERT INTO StagingCheckImage with the parsed values and a server-side GETDATE() timestamp.

Workflow 3: Wire Confirmation File Processing

Entry point: A file matching wire.txt detected in the watch directory.

Steps:

  1. Read all non-blank lines of the fixed-width text file.
  2. For each line, extract fields by character offsets: WireReference (columns 0–15), Amount (columns 16–27), Beneficiary (columns 28–67).
  3. Execute INSERT INTO StagingWireConfirmation for each line.
  4. The file is considered successful if at least one record was inserted. A file with all blank lines is treated as failed.

Workflow 4: Regulatory Feed File Processing

Entry point: A file matching (reg|feed).(csv|txt) detected in the watch directory.

Steps:

  1. Read all non-blank lines of the CSV or text file.
  2. Split each line by comma: FeedCode (field 0), RecordDate (field 1), Payload (field 2).
  3. Execute INSERT INTO StagingRegulatoryFeed for each line.
  4. The file is considered successful if at least one record was inserted.

Cross-Service Data Flows

ZavaFileIngestion is the sole service in this system's scope. There is no service-to-service HTTP or RPC communication. Cross-context data flows occur through two mechanisms:

  1. Staging tables → downstream consumers: Downstream ETL jobs or application services read from StagingCheckImage, StagingWireConfirmation, and StagingRegulatoryFeed in SQL Server. The ingestion service has no knowledge of these consumers and performs no cleanup or status update after initial INSERT.
  2. Event bus → downstream subscribers: After each file processing attempt, a file.ingestion event is published to the zava.events topic exchange in RabbitMQ with routing key file.ingested. Downstream subscribers (unknown to this service) can subscribe to this exchange to react to ingestion outcomes. If RabbitMQ is unavailable, the event publish silently fails — there is no retry, no dead-letter queue, and no compensating action. The file is moved to its destination directory regardless of the event publish outcome.

There is no aggregation, composition, or circuit-breaker fallback within this service.

Business Rules & Decision Logic

File Classification Rules

  • A file is classified as check_images if its lowercase name contains check and ends with .csv.
  • A file is classified as wire_confirmations if its lowercase name contains wire and ends with .txt.
  • A file is classified as regulatory_feeds if its lowercase name contains reg or feed and ends with .csv or .txt.
  • As a fallback, any file whose name contains check, wire, or reg (regardless of extension) is routed to the corresponding type using a static keyword map.
  • Files whose lowercase name contains processed or error are unconditionally skipped — this prevents reprocessing files that have already been moved and prevents infinite loops if the processed/error directories are children of the watch directory.
  • Files that are not regular files (directories, symlinks) are skipped.

Parsing Rules

  • Check image files: Only the first line is read. An empty file causes the record to be blank but still triggers an insert attempt with empty strings. Fields beyond index 2 are ignored.
  • Wire confirmation files: Fixed-width offsets (0–15, 16–27, 28–67) are extracted safely — if a line is shorter than the end offset, only the available characters are used (no exception thrown).
  • All parsers: Blank lines are skipped. All field values are stored as raw strings with no type coercion or format validation.

Success / Failure Rules

  • A file is considered successfully processed if at least one PreparedStatement.executeUpdate() call succeeds without exception.
  • A file is considered failed if: (a) an exception is thrown during file reading, (b) an exception is thrown during SQL insert, or (c) the file is a multi-line type and no non-blank lines were found.
  • For wire confirmation and regulatory feed files, partial success is possible — some lines may insert successfully while others fail. The file outcome reflects whether any insert succeeded (insertedAny || result). Partially inserted files are moved to /processed, leaving inconsistent data in the staging table with no record of which lines failed.

Transaction & Error Handling Rules

  • There are no database transactions — each INSERT is a separate auto-committed operation. There is no rollback mechanism.
  • SQL and AMQP failures are caught and logged to stdout only. No exception propagates to a dead-letter queue or retry mechanism.
  • File move failures (e.g., permissions error) are also logged and silently swallowed — the file may remain in the watch directory and be reprocessed on the next polling cycle.

  • No authorization checks are performed. Any process or user with write access to the watch directory can inject files into the ingestion pipeline.

Version & Compatibility Risks

The MSSQL JDBC driver 12.6.1.jre8 is a recent release and remains supported; however, it targets the jre8 variant, which ties the application to Java 8. Upgrading to Java 11+ would require switching to the jre11 (or later) artifact. The RabbitMQ AMQP client 5.21.0 is a recent stable release with no immediate end-of-life concerns, but it is a low-level client — migration to Azure Service Bus would require a complete messaging layer rewrite. Neither dependency includes a BOM or version management mechanism, so version upgrades must be managed manually in build.gradle.

Notable Observations

  • No logging framework declared: The application uses System.out.println exclusively. A structured logging library (e.g., SLF4J + Logback) is absent from the dependency list, which will hinder observability in cloud deployments.
  • No connection pooling: Both JDBC and AMQP connections are opened and closed per operation. No HikariCP, DBCP, or RabbitMQ connection-pool dependency is declared, creating high connection churn.
  • No DI or application framework: The service is written as a single static-method class with no framework (Spring, Quarkus, Micronaut). All wiring, lifecycle management, and configuration loading is hand-coded.
  • Minimal footprint but high migration surface: The two external dependencies map directly to Azure migration targets — MSSQL JDBC → Azure SQL Database, and RabbitMQ AMQP → Azure Service Bus — making the dependency surface small but each replacement significant.

Caching Strategy

No caching layer is present. The application does not use Spring Cache, Redis, EhCache, Caffeine, or any other caching mechanism. Every database insert creates a new JDBC connection and immediately closes it after the single statement executes.

Data Ownership Boundaries

The service owns all three staging tables exclusively. There is no evidence of other services sharing this database, but the tables are prefixed with Staging, suggesting they are intended as a landing zone for a downstream batch or ETL process to consume and promote records into production tables. The service only performs INSERT operations — downstream systems are responsible for reading, validating, and promoting staged data.

There is no service-to-service API access for data retrieval; all data flow is one-directional (file → staging table). No CQRS, event sourcing, or read-model patterns are implemented.

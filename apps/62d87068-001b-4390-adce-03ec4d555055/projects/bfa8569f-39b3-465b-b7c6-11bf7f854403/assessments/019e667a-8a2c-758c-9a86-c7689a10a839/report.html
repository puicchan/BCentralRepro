Data Storage & External Services

The application uses a single external data store: Microsoft SQL Server (database ZavaBankDB). All read and write operations go through direct JDBC connections managed by LedgerConnectionFactory. There are no caches, message brokers, or third-party API integrations. Configuration (DB host, port, name, credentials) is loaded from environment variables with a fallback to the ledger.properties classpath resource.

Key Architectural Decisions

  • Servlet-based, no framework: The application is built entirely on standard Java Servlets without a dependency-injection framework; component wiring is done via direct static calls.
  • Direct JDBC data access: SQL is hand-written with PreparedStatement; there is no ORM or repository abstraction layer.
  • Configuration via env-var override: LedgerConfig reads environment variables first (e.g., DB_HOST), falling back to ledger.properties, enabling container-friendly configuration injection.

No Spring Boot Actuator, Micrometer, Prometheus, or OpenTelemetry integration is present. There are no structured health indicators, no /metrics endpoint, and no distributed tracing instrumentation.

DTOs & Contracts

The application does not define standalone DTO classes. Instead, two private static inner classes are used inside TransactionServlet:

  • TransactionRequest (inner class): Captures the parsed transaction request body — debit/credit account IDs, amount, description, and reference number. Not immutable (mutable POJO with package-private fields).
  • TransactionResult (inner class): Carries the result of a successful transaction post — generated transaction IDs and updated balances. Not immutable.

All HTTP request/response payloads are hand-serialized XML strings. There is no OpenAPI/Swagger specification, no protobuf schema, no GraphQL schema, and no JSON serialization library (Jackson, Gson, etc.). LedgerXml provides manual XML character escaping for response output. For full field-level details, see data-architecture.md.

Communication Patterns

Synchronous only: The application accepts HTTP requests directly (no API gateway) and responds synchronously. All database access is synchronous JDBC via LedgerConnectionFactory.

No asynchronous messaging: No Kafka, RabbitMQ, Azure Service Bus, or any event-driven pattern is used.

No resilience patterns: There is no circuit breaker (Resilience4j, Hystrix), no retry policy, no timeout configuration, and no bulkhead pattern. A SQL Server connection failure results in a raw HTTP 500 response with no fallback.

No service discovery: The application is a single deployable unit with no client-side load balancing, Eureka, Consul, or Kubernetes service discovery.

No connection pooling: JDBC connections are opened per-request via DriverManager.getConnection() with no pooling (HikariCP, c3p0, DBCP). Under load this will exhaust available database connections.

Security posture: No authentication or authorization is implemented. All four endpoints are publicly accessible with no credentials, session tokens, JWT, OAuth2, Basic Auth, or role checks. Transport security (HTTPS/TLS) is not configured at the application level and would need to be provided by the servlet container or a reverse proxy. This means the POST /api/transactions endpoint — which posts financial transactions — is entirely unprotected.

Startup dependency chain: The application assumes the SQL Server database is available when the WAR starts. There are no readiness probes or wait mechanisms; requests that arrive before the database is ready will fail with a 500 error.

Core Business Workflows

ZavaLedger is a central banking ledger service that manages account balances and records financial transactions using a double-entry bookkeeping model — every fund movement is recorded as both a debit leg and a credit leg in a single atomic operation.

Primary Workflows

Workflow 1: Query Account Balance

A client requests the current and available balance for a specific account. The Servlet validates the URL path, extracts the numeric account ID, queries the database, and returns an XML balance response. If the account does not exist a 404 is returned.

Steps:

  1. Client calls GET /api/accounts/{id}/balance.
  2. Path segments are parsed; account ID is validated as a positive integer.
  3. A single SELECT query retrieves Balance and AvailableBalance from the Accounts table.
  4. If no row is found → respond NOT_FOUND (404).
  5. If found → respond OK (200) with both balance values in XML.

Workflow 2: Query Account Transaction History

A client requests a chronological list of all transaction legs for a specific account, newest first.

Steps:

  1. Client calls GET /api/accounts/{id}/transactions.
  2. Path segments are parsed; account ID is validated as a positive integer.
  3. A SELECT query retrieves all Transactions rows for the account, ordered by TransactionDate DESC, TransactionID DESC.
  4. Each row is serialized to an XML <transaction> element; special characters in text fields are escaped via LedgerXml.escape().
  5. Respond OK (200) with the full transaction list wrapped in <transactionsResponse>.

Workflow 3: Post a Double-Entry Financial Transaction

The core business operation: atomically transfer funds between two accounts. Every transfer creates two transaction legs — one debit (reducing the source account's balance) and one credit (increasing the destination account's balance) — ensuring the ledger remains in balance.

Steps:

  1. Client sends POST /api/transactions with an XML body containing debitAccountId, creditAccountId, amount, description, and referenceNumber.
  2. The XML body is parsed using a securely-configured DOM parser (external entity processing disabled).
  3. Business rule validation (see Business Rules section): debit ≠ credit account; amount > 0.
  4. A JDBC transaction is opened (autoCommit=false).
  5. Both account balances are read in the same transaction connection.
  6. Existence check: if either account does not exist → rollback, respond 400 Bad Request.
  7. The active debit TransactionType and credit TransactionType are looked up from the TransactionTypes table.
  8. New balances are computed: debitNewBalance = currentDebit − amount; creditNewBalance = currentCredit + amount.
  9. Both Accounts rows are updated (Balance, AvailableBalance, LastActivityDate, ModifiedDate).
  10. Two Transactions rows are inserted — one for the debit leg (negative amount) and one for the credit leg (positive amount); both record BalanceAfter, Description, ReferenceNumber, CounterpartyAccount.
  11. Commit on success; respond 200 POSTED with both generated TransactionIDs and new balances.
  12. Rollback on any SQLException or IllegalArgumentException; respond with appropriate error code.

Cross-Service Data Flows

ZavaLedger is a single service with no inter-service communication. There are no API gateway aggregation patterns, no downstream service calls, and no event-driven data flows. All data is read from and written to the single ZavaBankDB SQL Server database in direct JDBC calls. No fallback or circuit-breaker behavior exists across services; all resilience failures manifest as HTTP 500 responses.

Business Rules & Decision Logic

Validation Rules

RuleWhere EnforcedOutcome if Violated
Debit account ID and credit account ID must differTransactionServlet.parseRequest()IllegalArgumentException → HTTP 400

Decision Logic

  • Debit vs credit leg identification: TransactionTypes.IsDebit = true identifies debit-type transactions; false identifies credit-type. The first active type of each kind is used (SELECT TOP 1 … ORDER BY TransactionTypeID).
  • Balance update: Both Balance and AvailableBalance are set to the same computed new balance — there is no separate available-balance logic (e.g., holds or reserved amounts are not modelled).
  • CounterpartyAccount linkage: The debit leg records the credit account ID as its CounterpartyAccount and vice versa, providing a navigable cross-reference between paired legs.

State Transitions

Transactions are inserted with Status = 'Posted' and Channel = 'API' directly — there is no multi-step lifecycle (e.g., pending → posted → settled). All transactions are immediately final upon commit.

Transaction Boundaries

The entire double-entry operation (2 account updates + 2 transaction inserts) executes within a single JDBC transaction. Either all four writes succeed and commit together, or all are rolled back. There is no saga, compensating transaction, or eventual-consistency pattern.

Error Handling

  • IllegalArgumentException: business validation errors → HTTP 400 with descriptive XML message.
  • SQLException: database-level errors → HTTP 500 with a generic error message ("Unable to post transaction."). Specific SQL error details are not exposed to the caller.
  • No audit trail, business event log, or dead-letter queue is implemented.

Authorization

No authorization rules are implemented. There are no role checks, ownership validation (e.g., verifying the caller owns the queried account), or access-control lists. Any caller with network access can read any account's balance or post a transaction between any two accounts.

Version & Compatibility Risks

The javax.servlet-api 4.0.1 dependency targets the Jakarta EE 8 / Java EE 8 namespace (javax.). Servlet containers running Jakarta EE 9+ (which moved to the jakarta. namespace) will not be compatible without a migration. This is a known breaking namespace change introduced in Jakarta EE 9. The mssql-jdbc 12.8.1.jre11 driver is a recent release and is compatible with Java 11–21; no immediate compatibility risk is identified for the JDBC driver.

Notable Observations

  • No framework dependencies: The application uses only the bare Servlet API — there is no Spring, Quarkus, Jakarta CDI, or any other framework. This reduces the dependency footprint but means all cross-cutting concerns (connection pooling, dependency injection, validation) must be handled manually.
  • No connection pooling library: JDBC connections are opened on every request via DriverManager.getConnection(). Adding a connection pool (e.g., HikariCP) would be needed before deploying to a production cloud environment.
  • No logging framework declared: The project declares no SLF4J, Log4j2, or Logback dependency, meaning any logging relies on java.util.logging (JUL) or is absent entirely.
  • javax.* namespace lock-in: Using javax.servlet-api 4.0.1 ties the application to a Jakarta EE 8-compatible runtime. Migrating to Jakarta EE 10+ (Azure-recommended Tomcat 10+) would require renaming all javax.servlet imports to jakarta.servlet.

Reference count queries (e.g., findTransactionType) are executed on every POST /api/transactions request without any result caching.

Data Ownership Boundaries

ZavaLedger is a single-service, single-database application. All three tables (Accounts, Transactions, TransactionTypes) are owned by the one deployable unit and reside in the ZavaBankDB SQL Server database. There is no database-per-service isolation concern, no shared database with other services, and no cross-service data access pattern.

Read/write patterns:

  • Read-only: AccountServlet — balance and transaction history queries.
  • Read-write within a transaction: TransactionServlet — reads balances, updates both account records, and inserts two transaction rows atomically using an explicit JDBC transaction (serializable concern: no row-level locking is applied; concurrent transactions on the same accounts could introduce race conditions).

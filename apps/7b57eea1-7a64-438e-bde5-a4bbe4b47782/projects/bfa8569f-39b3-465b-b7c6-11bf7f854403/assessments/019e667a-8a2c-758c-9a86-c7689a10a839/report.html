Data Storage & External Services

The application uses a single Microsoft SQL Server database (ZavaBankDB) for all persistence needs, including user records (Users), active session tokens (SessionTokens), bank accounts (Accounts, AccountTypes), and payment transactions (Transactions). All database access is performed through raw JDBC using PreparedStatement calls managed by PayGatewayConnectionFactory. Two external HTTP services are consumed: the Auth Gateway (WhoAmI.ashx) is called via HTTP GET to resolve a .ZAVAAUTH Forms-Auth cookie into a session token, and the ZavaLedger API (/api/transactions) is called via HTTP POST with an XML payload to post debit/credit transactions and receive a confirmation status.

Key Architectural Decisions

  • Apache Struts 1 (Classic) MVC: The application uses the Struts 1 ActionServlet as a front controller that dispatches all .do requests to specific Action subclasses, a legacy pattern no longer maintained upstream.
  • Stateless JDBC data access: No ORM or connection pool is used; each request opens and closes a raw JDBC connection, relying on the SQL Server driver for connection management.
  • Dual-mode SSO: Session resolution supports multiple token delivery mechanisms (HTTP parameter, X-Session-Token header, Authorization: Bearer header, or .ZAVAAUTH cookie via the Auth Gateway), making the application compatible with both direct API clients and browser-based SSO.

DTOs & Contracts

The application uses Struts 1 ActionForm subclasses as request DTOs — these are mutable JavaBeans populated by the Struts framework from HTTP form POST parameters:

  • LoginForm — request DTO for POST /login.do; carries the sessionToken field submitted from the login HTML form.
  • PaymentForm — request DTO for POST /makePayment.do; carries accountId, amount, paymentType, and memo form fields.

Internal value objects (not API DTOs):

  • SessionUser — holds authenticated user identity stored in the HTTP session after successful login.
  • AccountOption — a view model for rendering bank account dropdown options.
  • PaymentHistoryRecord — a view model for rendering transaction history table rows.

There is no OpenAPI/Swagger specification, no Protobuf schema, no GraphQL schema, and no JSON serialization library (all responses are server-rendered HTML via JSP). Refer to data-architecture.md for field-level details and persistence mappings.

Communication Patterns

Synchronous REST (outbound):

  1. Auth Gateway (SsoSessionService → GET /WhoAmI.ashx): Called synchronously via HttpURLConnection when the incoming request carries a .ZAVAAUTH cookie and no explicit session token. The cookie value is forwarded as a Cookie header. Connect timeout: 3 000 ms; read timeout: 3 000 ms. The response is plain JSON; sessionToken is extracted with a manual string search. If the call fails or returns non-200, the token is treated as absent (soft fail).
  2. ZavaLedger API (PaymentAction → POST /api/transactions): Called synchronously via HttpURLConnection with an XML body (Content-Type: application/xml). Connect timeout: 8 000 ms; read timeout: 8 000 ms. A <status>POSTED</status> substring in the response body is required for success; any other response or exception results in a user-facing error message (soft fail). Payload is hand-assembled XML — no XML serialization library is used.

No asynchronous messaging (no Kafka, RabbitMQ, JMS, or Azure Service Bus), no service discovery (all downstream URLs are hardcoded in paygateway.properties or environment variables), no circuit breaker (Resilience4j, Hystrix, etc. are absent), and no client-side load balancing.

Security posture: There is no HTTPS/TLS configured at the application level (the WAR relies on the servlet container or a reverse proxy for TLS termination). Authentication is session-based: after login, the SessionUser object is stored in the HTTP HttpSession. All protected actions (/makePayment.do, /paymentHistory.do) check the session attribute and redirect to /login.do if absent — implemented manually in each action class with no centralized filter or interceptor. There is no CSRF protection, no HttpOnly/Secure cookie flags set by the application, and no authorization (RBAC) layer beyond the session presence check. All endpoints are accessible over plain HTTP with no transport-layer security enforced by the application itself.

Startup Dependency Chain

ZavaPayGateway has no orchestrated startup dependency chain. The application assumes the following services are already available when it starts, but performs no active waiting or readiness probing:

  1. SQL Server / ZavaBankDB — required immediately: any login attempt that reaches the database layer will silently fail if SQL Server is unavailable (SQLExceptions are caught and swallowed).
  2. Auth Gateway (/WhoAmI.ashx) — required for .ZAVAAUTH cookie-based login; called with a 3-second connect/read timeout; failure is treated as "token not found" (soft fail).
  3. ZavaLedger API — required for payment submission; called with an 8-second connect/read timeout; failure is reported as a user-facing error (soft fail).

There is no Docker Compose depends_on, no Kubernetes readiness probe, no dockerize wait-for-TCP, no Spring Cloud Config retry, and no health-check endpoint that reflects downstream availability. The /health.do endpoint always returns HTTP 200 regardless of backend connectivity.

Primary Workflows

Workflow 1: SSO Authentication / Login

A user navigates to the portal and must authenticate via a session token before accessing any payment feature. The session token may arrive through four channels: a form POST field, an X-Session-Token header, an Authorization: Bearer header, or a .ZAVAAUTH cookie (which triggers an additional Auth Gateway call to resolve the token).

Steps:

  1. Browser lands on /login.do (GET) — rendered login form is returned.
  2. User submits a session token (POST /login.do), or token is auto-detected from a header or cookie on any protected page request.
  3. SsoSessionService attempts to validate the token directly against the SessionTokens table (joined with Users), checking IsActive = 1 and ExpiresAt > GETDATE().
  4. If no explicit token is found and a .ZAVAAUTH cookie is present, SsoSessionService calls the Auth Gateway GET /WhoAmI.ashx, forwarding the cookie. The returned JSON sessionToken field is then re-validated against the database.
  5. On success, a SessionUser (userId + username) is stored in the HttpSession and the browser is redirected to /makePayment.do.
  6. On failure, the login form is re-rendered with an error message.

Business rules involved: Token must be active and not expired. User must be active (u.IsActive = 1). At most one valid session token is used (TOP 1, ordered by latest expiry).

Workflow 2: Payment Initiation

An authenticated user selects a source account, enters an amount and payment type, and submits a payment. The application validates the inputs, generates a reference number, and delegates the actual transaction record to ZavaLedger via an XML HTTP POST.

Steps:

  1. User navigates to /makePayment.do (GET) — session is verified; account list is loaded from Accounts JOIN AccountTypes (up to 30 active accounts).
  2. User fills the payment form (account, amount, payment type, optional memo) and submits POST /makePayment.do.
  3. Session is re-verified (or resolved if not yet cached).
  4. Input validation: account ID must be non-empty, amount must be non-empty and parseable as a positive decimal, payment type must be non-empty.
  5. A unique reference number is generated: "PGW-" + System.currentTimeMillis().
  6. Settlement account resolution: the configured LEDGER_SETTLEMENT_ACCOUNT_ID is used as the credit side of the transaction; if it equals the debit account, a fallback alternate ID is selected (account 2 if configured as 1, else account 1).
  7. PaymentAction calls ZavaLedger POST /api/transactions with an XML payload containing debit account ID, credit account ID, amount, description (ZavaPayGateway:<paymentType>:<memo>), and reference number.
  8. ZavaLedger response is checked for <status>POSTED</status> — if present, the browser is redirected to /paymentHistory.do with a success message. Otherwise, an error is shown on the payment form.

Business rules involved: Amount must be > 0. All three required fields must be present. The credit account (settlement) must differ from the debit account. Payment description is structured as ZavaPayGateway:<type>:<memo> — this acts as an implicit filter key for history retrieval.

Workflow 3: Payment History View

An authenticated user views the 75 most recent payment transactions initiated through this portal.

Steps:

  1. User navigates to /paymentHistory.do (GET).
  2. Session is verified (or resolved).
  3. PaymentHistoryAction queries Transactions JOIN Accounts for the top 75 rows where Description LIKE 'ZavaPayGateway:%', ordered by TransactionDate DESC.
  4. Each row's Description field is split on : to extract the payment type for display.
  5. Results are rendered as an HTML table in payment-history.jsp.

Business rules involved: Only transactions with a description prefix of ZavaPayGateway: are shown — this serves as an application-level namespace to filter out transactions created by other systems sharing the same ledger database.

Workflow 4: Health Check

A monitoring system or load balancer probes /health.do (GET or POST). HealthAction unconditionally returns HTTP 200 with the health.jsp view. No downstream service availability is checked.

Cross-Service Data Flows

ZavaPayGateway acts as a thin orchestration layer between the browser, Auth Gateway, SQL Server, and ZavaLedger:

  1. SSO cookie resolution (Auth Gateway): When a .ZAVAAUTH cookie is detected and no session token is otherwise available, SsoSessionService calls GET /WhoAmI.ashx on the Auth Gateway (3-second timeout). The extracted session token is then validated against the local SessionTokens database. If the Auth Gateway is unavailable or returns non-200, the user is treated as unauthenticated (soft fail — no degraded mode or partial session).
  2. Payment transaction posting (ZavaLedger): PaymentAction posts a hand-assembled XML body to ZavaLedger (8-second timeout). ZavaLedger is assumed to write the transaction to the shared Transactions table in ZavaBankDB. ZavaPayGateway does not write to Transactions itself; it only reads them back via PaymentHistoryAction. If ZavaLedger is unavailable, the payment fails with a user-facing error — there is no retry, queuing, or offline fallback.
  3. Shared database coupling: Transactions rows created by ZavaLedger are read directly by ZavaPayGateway. The Description LIKE 'ZavaPayGateway:%' filter is the only isolation boundary between this application's transactions and those from other systems using the same ledger.

Decision Logic

  • Settlement account self-debit avoidance: If the configured LEDGER_SETTLEMENT_ACCOUNT_ID equals the user's selected debit account, the system automatically switches the credit side to account ID 2 (if settlement is 1) or account ID 1 (otherwise). This avoids a zero-sum transaction to the same account.
  • Payment type enumeration: The UI constrains paymentType to ACH, BillPay, or Wire via a static HTML select element. No server-side enum validation is enforced.
  • History namespace filter: Only transactions with Description LIKE 'ZavaPayGateway:%' are shown, using the structured description prefix as an implicit namespace boundary within the shared Transactions table.

State Transitions

There are no explicit state machines. The only relevant state is the SessionTokens.IsActive flag (managed externally) and Accounts.Status = 'Active' (read-only filter). Transaction status is owned by ZavaLedger and displayed as-is.

Transaction Management

There is no application-level transaction management (@Transactional, Connection.setAutoCommit(false), etc.). Each JDBC connection auto-commits. The ZavaLedger call and the database reads are not coordinated — if ZavaLedger posts a transaction but the response is lost (e.g., network timeout), the application reports failure to the user but the transaction may already exist in the ledger (no idempotency key or compensation mechanism).

Error Handling

All SQLException exceptions in data access paths are silently swallowed (caught and ignored), returning empty results rather than surfacing errors to the user. External service failures (Auth Gateway, ZavaLedger) return soft-fail results. No business exception types, compensating transactions, or dead-letter handling are implemented.

Authorization

Beyond session presence, there is no role-based access control (RBAC), attribute-based access control (ABAC), or resource ownership enforcement. Any authenticated user can view all active accounts and all ZavaPayGateway:-prefixed transactions regardless of account ownership.

Version & Compatibility Risks

Apache Struts 1.3.10 is the most critical risk: Struts 1.x reached end-of-life in December 2013 and has received no security updates since. Multiple high-severity CVEs (including remote code execution vulnerabilities in the ClassLoader and ActionForm layers) affect the 1.x line. The javax.servlet-api:3.1.0 namespace will require migration to jakarta.servlet-api for any move to Jakarta EE 9+ or modern servlet containers beyond Tomcat 9. The Microsoft JDBC driver (12.8.1) is current and well-supported for Java 8 targets, presenting no immediate risk.

Notable Observations

  • Struts 1 is unmaintained and carries known CVEs: The Struts 1.x line has not received patches in over a decade and is a well-known migration target; migration to Spring MVC, Jakarta Faces, or another modern MVC framework is strongly recommended before any cloud deployment.
  • No logging library declared: There is no SLF4J, Log4j2, or Logback dependency in the build file; Struts 1 brings in commons-logging transitively, but structured/cloud-ready logging (e.g., JSON output) will require an explicit dependency addition.
  • No connection pooling: Database connectivity relies on raw DriverManager.getConnection() per request with no connection pool (HikariCP, DBCP2, etc.), which is a reliability and performance concern at scale.
  • Minimal dependency footprint: The application carries only 4 direct dependencies, making the technical surface area for library modernization small, but the Struts 1 framework is itself a large transitive dependency tree (commons-beanutils, commons-collections, commons-digester, etc.) with its own EOL concerns.

Caching Strategy

No caching layer is configured. There is no Spring Cache (@Cacheable), Redis, EhCache, Caffeine, or any second-level cache. The only in-memory state is the SessionUser object stored in the standard Servlet HttpSession after a successful SSO login — this avoids a repeated database round-trip per request for session validation within the same browser session, but it is not a true cache (no TTL, no eviction, and no distributed coherence).

Account lists and transaction history are fetched fresh from SQL Server on every page request.

Data Ownership Boundaries

ZavaPayGateway is the sole application accessing ZavaBankDB directly. All five tables (Users, SessionTokens, Accounts, AccountTypes, Transactions) are logically owned by the bank's shared SQL Server instance. The application reads users and session tokens for authentication, reads accounts for the payment form, and reads transactions for history display. It does not write to any table directly — payment transactions are created by the downstream ZavaLedger API (which presumably writes to the Transactions table via its own data access path). This creates an implicit shared-database coupling: ZavaPayGateway reads Transactions that ZavaLedger writes, with no explicit API contract or schema versioning boundary between them.

There are no CQRS patterns, no event sourcing, and no read-model projections. All reads are synchronous OLTP queries against the same operational database.

Data Storage & External Services

The application uses a single SQL Server database (ZavaBankDB) for customer/account/transaction data and integrates with external HTTP services for centralized authentication (AuthGateway) and ledger balance/transaction reads.

Key Architectural Decisions

  • Uses page code-behind with direct ADO.NET SQL commands instead of repository/ORM abstraction.
  • Uses Forms Authentication cookie and page-level authorization rules in web.config.
  • Implements dual-source transaction retrieval: primary from Ledger API with SQL fallback when remote call fails.

DTOs & Contracts

The application does not define dedicated API DTO classes. Contracts are represented by:

  • WebForms control-bound tabular datasets (DataTable) for customers, accounts, and transactions.
  • XML response contracts consumed from ledger endpoints (balance, availableBalance, transaction nodes).
  • Query-string contract on login (ReturnUrl) for redirect flow.

No immutable DTO records/classes or OpenAPI/protobuf/GraphQL specifications were found.

Communication Patterns

Communication is synchronous:

  • Browser to WebForms pages via HTTP requests and postbacks.
  • WebForms service logic to SQL Server via direct SqlCommand queries.
  • WebForms to external ledger/auth services via HttpWebRequest redirects/calls.

Resilience behavior is limited to exception fallback in transaction retrieval: on ledger request failure, the app falls back to local SQL query results. No explicit retry, timeout policy, or circuit breaker library was found.

Service discovery uses configured URLs in web.config; there is no dynamic discovery mechanism. Security posture is forms-auth cookie based with authorization rules for anonymous access only on Login/Logout pages; no explicit TLS enforcement settings are defined in project configuration.

The application supports teller/admin workflows for customer account lookup, account lifecycle actions, and transaction visibility with external ledger integration.

Primary Workflows

Workflow 1: Employee Authentication and Console Access

  1. User opens Login.aspx with optional ReturnUrl.
  2. App checks current authentication state.
  3. Unauthenticated users are redirected to the configured AuthGateway login URL.
  4. Authenticated users are redirected to Default.aspx.

Workflow 2: Customer Account Review

  1. Authenticated user loads Default.aspx.
  2. Application loads customer list and account types from SQL Server.
  3. User selects a customer.
  4. Application loads customer accounts and allows balance/history actions.

Workflow 3: Account Action Handling

  1. User chooses one action: show balance, show transactions, or close account.
  2. Balance and transaction actions call ledger services first.
  3. If transaction retrieval from ledger fails, SQL fallback is used.
  4. Close-account action updates account status and timestamps in SQL Server.

Cross-Service Data Flows

The portal composes account-management data from local SQL tables with external ledger data. Account metadata is sourced locally, while near-real-time balance/history is requested from ledger APIs. When ledger retrieval fails, transaction history degrades gracefully to local SQL data, allowing partial workflow completion.

Business Rules & Decision Logic

  • Access rule: only authenticated users can access Default.aspx; Login and Logout are explicitly open.
  • Input rule: opening a new account requires valid CustomerId, AccountTypeId, and numeric opening balance.
  • Account state rule: close-account action sets status to Closed and updates close/modified timestamps.
  • Resilience rule: transaction history uses ledger as primary source with local SQL fallback when external call fails.

Data Storage & External Services

The service uses a single SQL Server database (ZavaBankDB) and reads/writes operational risk data directly through SQL queries. External dependency is limited to runtime-provided environment variables for database connection overrides.

Key Architectural Decisions

  • Uses a single-service SOAP contract (IRiskEngineService) instead of REST endpoints.
  • Implements direct SQL with explicit commands and transactions rather than ORM/repository abstractions.
  • Provides lightweight health probing via a standalone HealthHandler.

No asynchronous messaging, circuit breaker library, or retry policy framework is configured in code. Service discovery and gateway aggregation are not present for this single-service repository. Security posture: no explicit API authentication/authorization or TLS enforcement is configured in this repository; endpoint exposure is controlled by hosting/runtime configuration.

Core Business Workflows

This service supports the banking risk domain by scoring loan applications and exposing customer risk factors for downstream decisioning. It also allows controlled updates to risk model parameters used in scoring.

Primary Workflows

Workflow 1: Score Loan Application

  1. Caller submits ScoreLoanApplication with an application ID.
  2. Service validates input and rejects invalid IDs.
  3. Service reads loan, account, and latest credit data.
  4. Service loads configurable model weights and computes normalized weighted score.
  5. Service derives rating bucket and recommended approval amount.
  6. Service stores the resulting assessment and returns a scoring response.

Workflow 2: Get Customer Risk Factors

  1. Caller submits GetRiskFactors with a customer ID.
  2. Service validates input and queries risk signals (credit score, exposure, balances, account activity).
  3. Service loads active factor metadata and computes weighted impact values.
  4. Service returns overall factor-based risk summary.

Workflow 3: Update Risk Model Parameters

  1. Caller submits UpdateRiskModel with one or more parameter updates.
  2. Service validates payload and opens a transaction.
  3. Each parameter is upserted into the model parameter store.
  4. Transaction is committed and update summary is returned.

Cross-Service Data Flows

No cross-service composition is implemented in this repository. All workflow inputs and outputs are handled inside a single service boundary using a shared SQL data source.

Business Workflow Sequence

sequenceDiagram participant Caller participant Service as "ZavaRiskEngineService" participant DB as "ZavaBankDB" Caller->>Service: ScoreLoanApplication(applicationId) Service->>Service: Validate application ID Service->>DB: Load loan, account, and credit inputs DB-->>Service: Input dataset Service->>DB: Load model parameters DB-->>Service: Parameter set Service->>Service: Calculate score, rating, approved amount Service->>DB: Save risk assessment DB-->>Service: Persisted Service-->>Caller: RiskScoreResponse

Business Rules & Decision Logic

  • Input IDs must be greater than zero; invalid input returns a fault.
  • Scoring formula combines normalized credit score, balance-to-loan ratio, term, and requested amount using configurable weights.
  • Rating thresholds map numeric score to A-F buckets.
  • Approval multiplier is rating-dependent (higher rating permits higher approved amount).
  • Model parameter updates are transactional to avoid partial writes.

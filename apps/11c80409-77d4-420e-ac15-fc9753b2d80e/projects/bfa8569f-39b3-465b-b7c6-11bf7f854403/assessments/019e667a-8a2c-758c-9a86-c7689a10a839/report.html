Data Storage & External Services

The application uses a single SQL Server database (ZavaBankDB) for identity and session persistence, with no separate cache or message broker. It also integrates with downstream Zava services by exposing token validation and identity lookup responses that can be consumed for SSO propagation.

Key Architectural Decisions

  • Uses a centralized AuthRepository with parameterized SQL for all persistence interactions instead of an ORM.
  • Uses Forms Authentication ticket UserData to carry the session token for cross-service SSO handoff.
  • Keeps operational endpoints lightweight (/health, /api/auth/validate, WhoAmI.ashx) alongside Web Forms pages.

DTOs & Contracts

The codebase uses lightweight service-level contract classes rather than separate gateway aggregation DTOs. AuthUser represents account-level identity data loaded from persistence and SessionValidationResult represents token validation responses for API clients. Both are mutable class-based models. JSON responses for /api/auth/validate and /WhoAmI.ashx are manually serialized string payloads rather than schema-first contracts. No OpenAPI/Swagger spec, protobuf schema, or GraphQL schema was found.

Communication Patterns

All communication is synchronous: incoming HTTP requests are processed by Web Forms pages/handlers, then immediate SQL queries are executed via AuthRepository. No asynchronous message queue, event bus, or pub/sub integration was identified. Retry/circuit-breaker libraries and explicit timeout policies are not configured in code. Service discovery is not used because this is a single deployable service with direct database connectivity. Startup ordering has one effective dependency: the SQL Server backend must be reachable for login/token operations to succeed. Security posture includes Forms Authentication cookie handling and authorization rules in web.config; transport-level TLS enforcement is not configured in this codebase and depends on external hosting termination.

Core Business Workflows

ZavaAuthGateway governs user sign-in, session lifecycle, and identity handoff for the wider Zava Bank platform. Its workflows focus on validating credentials, issuing tokens, and serving authenticated identity context to dependent applications.

Primary Workflows

Workflow 1: User Login and Session Issuance

Entry point: Login.aspx form submission.

  1. User submits username/password.
  2. Service loads account record and validates account is active and not locked.
  3. Service verifies password hash against stored salt+hash.
  4. On success, service creates a new session token and updates last login timestamp.
  5. Service issues forms authentication cookie and redirects to authenticated landing page.

Workflow 2: Session Validation for Downstream Consumers

Entry point: GET /api/auth/validate with token query/header.

  1. Caller submits session token.
  2. Service verifies token exists, is active, and is not expired.
  3. Service returns contract response indicating valid/invalid state, and includes user context when valid.

Workflow 3: Identity Introspection and Logout

Entry points: GET WhoAmI.ashx and GET Logout.aspx.

  1. WhoAmI flow decrypts auth cookie, confirms account status, and loads role memberships.
  2. Service returns authenticated identity payload including session token for cross-ecosystem SSO handoff.
  3. Logout flow deactivates persisted session token when available, signs out cookie, and redirects to login.

Cross-Service Data Flows

This repository implements one deployable service; cross-service interaction occurs through contract consumption by other Zava applications. The gateway publishes two integration responses: token validity (/api/auth/validate) and authenticated identity context (WhoAmI.ashx). Identity payload includes sessionToken so downstream services that cannot decrypt forms cookies can still perform trust handoff. When validation fails (missing/invalid/expired token), fallback behavior is to return explicit unauthenticated/invalid responses rather than partial identity data.

Business Rules & Decision Logic

  • Credentials are mandatory; empty username/password is rejected before persistence access.
  • Account status gating: users must be active and not locked out to authenticate or resolve identity.
  • Session validity requires token to be active and unexpired, and linked user must still be active.
  • Successful login creates a session token with a 30-minute expiration window.
  • Logout invalidates persisted token state when possible, then expires the auth cookie.
  • Authorization model is forms-auth based, with selected paths (Login.aspx, Default.aspx, Logout.aspx, api/auth/validate, health, WhoAmI.ashx) explicitly allowed in configuration.

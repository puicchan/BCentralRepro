The service uses a SQL Server database (ZavaBankDB) as its primary data store and reads/writes account, transaction, statement request, generated statement, and archive data. No cache layer or message broker is configured in this repository, and no external third-party HTTP APIs are referenced in source.

Key Architectural Decisions

  • Uses WCF basicHttpBinding for service exposure through StatementService.svc.
  • Uses direct SQL commands (ADO.NET) instead of ORM abstractions.
  • Supports runtime database configuration override via environment variables before falling back to web.config.

Core Business Workflows

This service supports customer statement retrieval workflows for a banking domain. The central business process is generating monthly statements from transaction history and storing generated artifacts for later retrieval.

Primary Workflows

Workflow 1: Generate Monthly Statement

  1. Client invokes the statement generation operation with account and period inputs.
  2. Service validates account and date range rules.
  3. Service loads account owner and transaction history for the period.
  4. Service computes credits/debits and renders HTML statement output.
  5. Service persists request, generated statement, and archive metadata.
  6. Service returns generated statement details.

Workflow 2: Retrieve Statement History

  1. Client requests statement history for an account.
  2. Service validates input and loads recent generated statement records.
  3. Service returns ordered history items.

Workflow 3: Retrieve Statement Detail

  1. Client requests a specific statement by identifier.
  2. Service validates identifier and loads full statement content.
  3. Service returns statement detail response or not-found fault.

Cross-Service Data Flows

The workflow composes statement output from customer/account/transaction data and then augments it with generated statement persistence data in the same SQL Server environment. No separate gateway or downstream service composition is implemented in this repository, so fallback behavior is limited to returning SOAP faults when required data is missing.

Business Workflow Sequence

sequenceDiagram participant Client participant Service as "StatementService" participant DB as "SQL Server" Client->>Service: Request monthly statement for account and period Service->>Service: Validate account and period business rules Service->>DB: Load account owner and period transactions DB-->>Service: Customer, account, and transaction records Service->>Service: Calculate totals and render statement content Service->>DB: Persist request, generated statement, archive DB-->>Service: Persisted statement identifiers Service-->>Client: Generated statement response

Business Rules & Decision Logic

  • accountId must be greater than 0; invalid values return a fault.
  • month must be in range 1-12 and year must be in range 2000-2100.
  • Credit/debit totals are derived from transaction type and amount sign.
  • If account or statement records are missing, the service returns explicit fault responses.
  • Generated statement content is checksummed before archival metadata insert.

Version & Compatibility Risks

The service targets .NET Framework 4.8, which is a legacy runtime compared to modern .NET (net8+). WCF server hosting with System.ServiceModel and ASP.NET System.Web are key modernization considerations for upgrade to current .NET versions.

Notable Observations

  • Data access is implemented via raw SQL (System.Data) rather than ORM, reducing ORM migration concerns but increasing manual query migration effort.

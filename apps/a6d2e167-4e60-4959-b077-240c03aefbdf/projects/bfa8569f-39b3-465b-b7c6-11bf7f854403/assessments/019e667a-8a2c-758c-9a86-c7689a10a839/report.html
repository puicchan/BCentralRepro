Data Storage & External Services

The application uses a single Microsoft SQL Server instance (default host sqlserver, port 1433, database ZavaBankDB) as its only data store. Two tables are used: KYCWatchlist holds flagged names from compliance sources (e.g. OFAC), and KYCVerification stores the audit trail of every verification result. Connection parameters are read from environment variables (DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD) with fallback to kyc.properties on the classpath. There are no caches, message brokers, or third-party external services.

Key Architectural Decisions

  • Direct JDBC without ORM: SQL queries are written by hand using PreparedStatement, keeping the dependency footprint minimal and avoiding framework overhead.
  • Schema bootstrap on startup: KycBootstrapServlet is configured with load-on-startup=1 and creates the required tables and seed data on first deployment using idempotent DDL, so no external migration tooling is needed.
  • Configuration via environment variables with property file fallback: KycConfig reads connection details from environment variables first and falls back to kyc.properties, enabling both containerised and local-development deployment.

All four endpoints — including /api/kyc/verify (which processes sensitive personal identity data) and /api/kyc/status/{id} (which returns that data) — are publicly accessible with no credentials or role checks of any kind. Core Business Workflows

ZavaKYCService is a Know Your Customer (KYC) compliance service that verifies customer identities by screening submitted names against a sanctions/watchlist and recording the outcome for regulatory audit purposes.

This is a single-service application with no inter-service communication. The upstream banking system is an implicit external actor that calls the KYC API but is not part of this codebase.

Primary Workflows

Workflow 1: KYC Identity Verification

Entry point: POST /api/kyc/verify

A calling system (e.g. a customer onboarding portal) submits a customer's identity details. The service screens the name against the watchlist, records the decision, and returns an immediate synchronous verdict.

Steps:

  1. Receive and parse request — The servlet reads the raw HTTP body and parses it as JSON. If the body is not valid JSON, a 400 Bad Request is returned immediately.
  2. Input validation — customerId must be a positive integer and fullName must be non-empty. If either check fails, a 400 Bad Request is returned with a descriptive error message. idNumber is optional.
  3. Open database connection — A new JDBC connection is obtained from KycConnectionFactory. If SQL Server is unreachable, a 500 Internal Server Error is returned.
  4. Watchlist screening — The submitted fullName is compared case-insensitively against every name in KYCWatchlist. A single-row SELECT TOP 1 query is used; any match triggers a REVIEW decision.
  5. Decision assignment — If a watchlist match is found, status = "REVIEW" and reason = "Name matched watchlist.". Otherwise, status = "PASS" and reason = "No watchlist match.".
  6. Audit record insertion — A new row is written to KYCVerification containing customerId, fullName, idNumber, status, reason, and the current server timestamp (GETDATE()).
  7. Return verdict — A 200 OK JSON response is returned with { customerId, status, reason }.

Workflow 2: KYC Status Enquiry

Entry point: GET /api/kyc/status/{customerId}

A calling system queries the most recent KYC decision for a given customer.

Steps:

  1. Extract and validate path parameter — customerId is parsed from the URL path. If absent or non-numeric, a 400 Bad Request is returned.
  2. Open database connection — A new JDBC connection is obtained. If SQL Server is unreachable, a 500 Internal Server Error is returned.
  3. Retrieve latest verification record — The most recent KYCVerification row for the customer is fetched, ordered by VerifiedDate DESC, VerificationID DESC.
  4. Return result or 404 — If a record exists, a 200 OK JSON response is returned with the full verification details. If no record exists, 404 Not Found with { status: "NOT_FOUND" }.

Workflow 3: Schema Bootstrap (Startup)

Entry point: KycBootstrapServlet.init() — triggered automatically by Tomcat on application startup (load-on-startup=1).

This workflow runs once on every cold start before the API becomes available.

Steps:

  1. Open database connection — Connect to SQL Server. If unavailable, the application fails to start.
  2. Idempotent schema creation — Execute DDL to create KYCWatchlist and KYCVerification tables if they do not already exist.
  3. Seed initial watchlist data — If KYCWatchlist is empty, insert a sample entry (John Alias / OFAC-SAMPLE) so the service is functional immediately after a fresh deployment.

Cross-Service Data Flows

This is a single-service application. There are no inter-service data flows, no gateway aggregation, and no event-driven communication. All data originates from the HTTP request body or from the SQL Server database. The only external actor is the upstream banking system that calls the two API endpoints; it is not a discoverable service within this codebase.

When the visits-service pattern is absent (as here), there is no fallback composition logic to document.

State Transitions

KYCVerification records are immutable once written (insert-only). Each verification request creates a new row; historical records are never updated or deleted. The status endpoint always returns the most recent record, so a customer can move from REVIEW to PASS (or vice versa) across separate verification requests.


[No record] → PASS  (first check, name not on watchlist)
[No record] → REVIEW  (first check, name on watchlist)
PASS        → REVIEW  (re-check after watchlist update)
REVIEW      → PASS    (re-check after watchlist correction)

Cross-Cutting Concerns

  • Transactions: No explicit transaction boundaries. Each SQL statement runs in its own auto-committed connection. An INSERT failure after a successful SELECT would leave no audit record; the HTTP response would be 500.
  • Error handling: SQLException is caught and results in a 500 response. The exception is not logged anywhere — it is silently discarded. catch (... ignored) patterns are used throughout.
  • Audit trail: Every successful verification writes a row to KYCVerification, providing an append-only audit log. There is no event log or structured audit framework.
  • Authorization: No authentication or authorization is implemented. Any caller with network access can submit verifications or retrieve results for any customerId.
  • Idempotency: Verification is not idempotent. Submitting the same customerId and fullName twice creates two separate KYCVerification rows. There is no deduplication or replay protection.

Version & Compatibility Risks

The org.json library is pinned to version 20140107 — a build from January 2014, over a decade old. While the API is stable, many security and correctness fixes have been released since then; the current release is 20240303. The javax.servlet-api 4.0.1 dependency targets the legacy javax. namespace (Java EE 8 / Servlet 4.0), which was superseded by the jakarta. namespace in Jakarta EE 9+. Migrating to a modern servlet container (Tomcat 10+) or cloud runtime would require a namespace migration from javax.servlet to jakarta.servlet. The mssql-jdbc 12.6.3.jre8 driver is recent, but it is the JRE 8 variant; upgrading the JDK to 11 or 17 would allow switching to the jre11 or jre17 jar which enables more modern TLS and authentication options.

Notable Observations

  • Severely outdated JSON library: org.json:json:20140107 is approximately 10 years behind the current release. Replacing it with 20240303 (or switching to Jackson/Gson) eliminates known parsing edge-case bugs and potential security issues.
  • Legacy javax.* namespace: All servlet imports use the javax.servlet package. This is incompatible with Tomcat 10+, WildFly 27+, and any Jakarta EE 10 container. A namespace migration is required before upgrading the servlet container.
  • No logging framework: The application has no logging dependency (no SLF4J, Log4j, Logback, or java.util.logging configuration). Errors are silently swallowed with empty catch (... ignored) blocks, which makes production diagnosis very difficult.
  • Minimal dependency surface: With only 3 declared dependencies the application is lightweight and easy to containerise, but the absence of a connection pool (e.g. HikariCP) means a new JDBC connection is opened for every HTTP request, which is a scalability concern.

Caching Strategy

No caching layer is implemented. Every read request executes a live SQL query against SQL Server. There is no application-level cache, no second-level ORM cache (no ORM is used), no distributed cache (Redis, Memcached), and no HTTP response caching. For a read-heavy KYC status endpoint this represents a potential scalability gap; watchlist lookups in particular could benefit from a short-lived in-memory cache given that the watchlist changes infrequently.

Data Ownership Boundaries

The application uses a single shared SQL Server instance with a single database (ZavaBankDB). There is only one service, so there are no cross-service data access concerns. Both tables (KYCWatchlist and KYCVerification) are fully owned and managed by the ZavaKYCService WAR.

Write operations always go through KycVerifyServlet (one INSERT per verification request). Read operations on KYCVerification are served by KycStatusServlet. There is no CQRS separation, no read replica, and no event sourcing.

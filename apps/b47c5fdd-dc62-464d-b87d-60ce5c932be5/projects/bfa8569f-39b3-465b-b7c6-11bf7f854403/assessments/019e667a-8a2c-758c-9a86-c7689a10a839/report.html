Data Storage & External Services

The application uses a Microsoft SQL Server database (ZavaBankDB) to persist wire transfer records in the WireTransfers table, accessed directly via JDBC (no ORM layer). Two synchronous HTTP services are called during transfer initiation: a Currency Service provides real-time FX rates for non-USD transfers, and a Ledger Service posts debit entries via an XML payload. After persisting a transfer, the service publishes an event to a RabbitMQ topic exchange (wire.events) with routing keys scoped by transfer status (e.g., wire.posted, wire.pending_ledger), enabling downstream consumers to react to wire events asynchronously.

Key Architectural Decisions

  • Raw Servlet with no framework: The application uses plain Jakarta EE HttpServlet without Spring, Quarkus, or any DI container — all configuration and dependencies are wired manually through static utility classes (WireConfig, WireConnectionFactory).
  • Direct JDBC without connection pooling: Database connections are created via DriverManager.getConnection() on each request, meaning there is no connection pool; this is a scalability concern for production workloads.
  • Config resolved from environment variables with property-file fallback: WireConfig reads each configuration value first from an environment variable (e.g., DB_HOST, RABBITMQ_HOST) and falls back to wire-transfer.properties, supporting both containerized deployment and local development.

Communication Patterns

Synchronous (outbound HTTP)

The service makes two synchronous blocking HTTP calls per wire transfer request using raw java.net.HttpURLConnection:

  1. Currency Service — GET {CURRENCY_SERVICE_BASE_URL}/api/currency/rate?from=USD&to={currency} — fetches the FX rate for non-USD transfers. Connect and read timeout: 7,000 ms each. On any failure (exception, non-2xx), the FX rate falls back silently to 1.0 (no error surfaced to the caller).
  2. Ledger Service — POST {LEDGER_SERVICE_BASE_URL}/api/transactions — posts a debit transaction as an XML payload (Content-Type: application/xml). Connect and read timeout: 7,000 ms each. On failure, the transfer is saved with Status = PENDING_LEDGER rather than POSTED; no retry is attempted.

There is no circuit breaker, no retry policy, and no bulkhead configuration. Both HTTP calls are fire-and-forget best-effort with silent fallback.

Service discovery is not implemented. Downstream service URLs are resolved from environment variables (CURRENCY_SERVICE_BASE_URL, LEDGER_SERVICE_BASE_URL) with a wire-transfer.properties fallback — services are addressed by hardcoded hostname strings (e.g., http://zava-currency-service:8080, http://zava-ledger:8080).

Asynchronous (RabbitMQ)

After persisting each wire transfer, the service publishes a domain event to a RabbitMQ topic exchange (wire.events) using the official amqp-client library. The routing key is {RABBITMQ_ROUTING_KEY_PREFIX}.{status.toLowerCase()} (e.g., wire.posted, wire.pending_ledger). Publishing failures are silently swallowed; there is no dead-letter queue, no publisher confirm, and no retry on failed publish.

Startup dependency chain

WireBootstrapServlet is registered with load-on-startup=1 in web.xml, meaning it executes before any HTTP traffic is accepted. It creates the WireTransfers SQL Server table if absent. If SQL Server is unavailable at startup, the servlet container will fail to start. For full probe and wait mechanism details, refer to configuration-inventory.md.

Security posture

No authentication, authorization, or TLS is configured at any level. All three HTTP endpoints (/health, /api/wire/transfer, /api/wire/{id}/status) are publicly accessible with no credential checks, no JWT/OAuth2/Basic Auth, and no HTTPS enforcement. The /api/wire/transfer endpoint in particular accepts financial transaction requests without any caller identity verification.

Primary Workflows

Workflow 1: Initiate Wire Transfer

Entry point: POST /api/wire/transfer (client submits a wire transfer request)

This is the core business workflow. It spans three external services and involves currency conversion, ledger accounting, persistence, and event notification.

Steps:

  1. Parse and validate request: Read JSON body; require fromAccountId > 0, non-empty toAccountNumber, non-empty toRoutingNumber, non-empty beneficiaryName, and amount > 0. Return HTTP 400 on any failure.
  2. Validate routing number format: Apply ABA routing number checksum algorithm (3-7-1 digit weighting on all 9 digits; sum must be divisible by 10). Return HTTP 400 if invalid.
  3. Determine transfer type: If currencyCode != "USD", classify as international and proceed to FX lookup; otherwise treat as domestic (fxRate = 1.0, debitAmountUSD = amount).
  4. Retrieve FX rate (international only): Call Currency Service. On success, use the returned rate. On failure or timeout (7 s), silently fall back to fxRate = 1.0.
  5. Compute debit amount: debitAmountUSD = amount × fxRate (rounded half-up to 2 decimal places).
  6. Generate reference number: Create a unique transfer reference: "WIRE-" + first 8 chars of UUID (uppercased).
  7. Post ledger debit: Call Ledger Service with an XML debit entry (fromAccountId → settlement account, USD amount, reference number). On success, set status = "POSTED". On failure or timeout (7 s), set status = "PENDING_LEDGER" with failureReason = "Ledger posting failed." No retry is attempted.
  8. Persist wire transfer: Insert a new WireTransfers record with all fields. Return HTTP 500 if the insert fails; the caller receives no transfer ID in this case.
  9. Publish wire event: Publish a JSON event to RabbitMQ topic exchange wire.events with routing key wire.{status.toLowerCase()}. Publishing failures are silently swallowed.
  10. Return response: HTTP 200 with wireTransferId, status, referenceNumber, fxRate, debitAmountUSD, and ledgerPosted flag.

Workflow 2: Query Wire Transfer Status

Entry point: GET /api/wire/{id}/status

A simple read workflow that retrieves the current state of a previously initiated wire transfer.

Steps:

  1. Parse and validate path: Extract {id} from the URL path. Return HTTP 400 if the path format is unexpected or id is not numeric.
  2. Look up transfer: Query WireTransfers by WireTransferID. Return HTTP 404 if not found.
  3. Return status: HTTP 200 with the full transfer status record (see data-architecture.md for field details).

Workflow 3: Database Bootstrap (Startup)

Entry point: Servlet container startup (WireBootstrapServlet, load-on-startup=1)

Ensures the WireTransfers table exists before the service accepts any HTTP traffic.

Steps:

  1. Connect to SQL Server: Open a JDBC connection using configured credentials.
  2. Create table if absent: Execute an idempotent IF OBJECT_ID(...) IS NULL CREATE TABLE WireTransfers (...) DDL statement.
  3. On failure: Throw ServletException, causing the servlet container to abort deployment.

Cross-Service Data Flows

Wire Transfer Initiation (multi-service composition)

The POST /api/wire/transfer workflow composes data from three external systems:

  1. Currency Service → ZavaWireTransferService: When a non-USD transfer is requested, the service calls GET /api/currency/rate?from=USD&to={currency} and reads the rate field from the JSON response. This rate is applied to compute debitAmountUSD. If the Currency Service is unavailable, the business fallback is to treat the FX rate as 1:1 — the customer is debited the nominal amount in USD regardless of actual market rate. This is a significant business risk for international transfers.
  2. ZavaWireTransferService → Ledger Service: The service posts an XML debit entry to POST /api/transactions, transferring funds from the customer's account (fromAccountId) to the bank's settlement account (ledger.settlement.accountId). The Ledger Service is the authoritative record of the debit. If the Ledger Service is unavailable, the transfer is saved with PENDING_LEDGER status, meaning the record exists in the wire transfer database but no actual funds have been moved. There is no compensating action, retry job, or reconciliation process to recover PENDING_LEDGER records.
  3. ZavaWireTransferService → RabbitMQ consumers: After each transfer is persisted, a domain event is published to the wire.events exchange. Downstream consumers (e.g., notification service, fraud detection, compliance reporting) can subscribe to routing keys such as wire.posted or wire.pending_ledger. If RabbitMQ is unavailable, the event is lost — there is no outbox pattern or guaranteed delivery.

Business Constraints & Decision Logic

  • International detection: A transfer is classified as international solely by checking whether currencyCode != "USD". There is no country validation, OFAC/sanctions list check, or regulatory threshold check.
  • FX rate fallback: If the Currency Service is unavailable, the FX rate defaults to 1.0. This means a customer requesting an international transfer in a foreign currency is debited only the face amount (no FX adjustment), representing a potential financial loss to the bank.
  • Settlement account: All ledger debits credit a single configurable settlement account ID (ledger.settlement.accountId), regardless of the destination bank or currency.
  • Reference number generation: Generated as "WIRE-" + first 8 characters of a random UUID (upper-cased). No collision detection is performed; the reference number is stored but not enforced as unique in the database schema.

Cross-Cutting Concerns

  • Transactions: No explicit transaction management. Each JDBC operation uses a single connection without a transaction wrapper. The FX call, ledger call, DB insert, and MQ publish are not coordinated in any distributed transaction or saga — a failure at any step after the DB insert leaves data in an inconsistent state relative to the ledger or event log.
  • Error handling: HTTP errors from external services are silently swallowed. There are no business exception types, compensating actions, or dead-letter queue handling.
  • Audit / logging: No structured logging or audit trail is implemented. Business events are partially captured via RabbitMQ event publishing, but only for successful DB inserts — there is no log of failed transfers, validation rejections, or external service errors.
  • Authorization: No authentication or authorization is enforced. Any caller can initiate a wire transfer on behalf of any fromAccountId — there is no verification that the caller owns or has authority over the originating account.

Version & Compatibility Risks

The most significant version risk is org.json:json:20140107, which is a release from 2014 — over a decade old and far behind the current release line. While functionally stable, it lacks modern features and the very old version identifier may trigger vulnerability scanners. The javax.servlet-api:4.0.1 dependency targets the javax.* namespace (Jakarta EE 8 era); migration to a Jakarta EE 10+ container would require switching to the jakarta.servlet-api namespace and bumping the Servlet API version. The mssql-jdbc:12.6.3.jre11 driver is relatively current (released 2024) and targets Java 11, so no immediate JDBC driver risk exists. The amqp-client:5.20.0 RabbitMQ client is also recent and stable.

Notable Observations

  • No connection pooling library: Database connections are opened via raw DriverManager.getConnection() on every request. No HikariCP, DBCP2, or equivalent pooling library is declared, which is a scalability and resource risk in production under load.
  • No logging framework: There is no SLF4J, Logback, Log4j2, or any other logging library declared. The application appears to silently swallow exceptions (catch (Exception ignored)) with no structured log output, making operational observability difficult.
  • org.json version is extremely stale: org.json:json:20140107 is pinned to a 2014 artifact. Modern alternatives such as Jackson Databind or Gson are more actively maintained, offer better performance, and have richer feature sets for JSON handling in Java applications.
  • javax. namespace signals legacy Servlet container dependency: The use of javax.servlet-api (rather than jakarta.servlet-api) locks the application to a Servlet 4.0-compatible container (e.g., Tomcat 9, WildFly 26). Moving to Tomcat 10+, Jetty 11+, or any Jakarta EE 10 runtime requires a namespace migration from javax. to jakarta.*.

Caching Strategy

No caching layer is implemented. There is no Redis, EhCache, Caffeine, Spring Cache, or any equivalent in-process cache. Every read request issues a fresh SQL query against SQL Server, and every write opens a new JDBC connection.

Data Ownership Boundaries

ZavaWireTransferService operates an isolated data store: it is the sole owner of the WireTransfers table in ZavaBankDB. No other service is known to read from or write to this database directly.

Cross-service data access is outbound only and performed via synchronous HTTP calls (not direct DB access):

  • The Ledger Service owns account and transaction records; ZavaWireTransferService posts debit entries via a REST/XML call rather than writing to the ledger's database.
  • The Currency Service owns exchange rate data; ZavaWireTransferService reads rates via HTTP REST.

There is no CQRS pattern, no event sourcing, and no read replica. All reads and writes target the single SQL Server instance.

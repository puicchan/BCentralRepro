Data Storage & External Services

The application has no local database. Its sole external dependency is a RabbitMQ broker (default host rabbitmq:5672, virtual host /zavabank). Processed records are published to the topic exchange filedrop.events with routing keys derived from the file extension (filedrop.csv, filedrop.txt, filedrop.dat). Files that cannot be processed are dead-lettered to the fanout exchange zava.dlx. Persistent file-system directories (/shared/filedrop, /shared/filedrop/processed, /shared/filedrop/error) serve as the input queue and audit trail.

Key Architectural Decisions

  • Dual-trigger ingestion: Combines a FileSystemWatcher for low-latency event detection with a periodic polling loop (configurable via WORKER_POLL_INTERVAL_MS) to handle files that may be missed during watcher startup or reconnection.
  • Dead-letter pattern: Failed files are published to a dedicated Fanout dead-letter exchange before being moved to an error directory, enabling downstream consumers to react to processing failures without blocking the main flow.
  • Environment-first configuration: All settings resolve from environment variables first, then fall back to app.config appSettings, then to hard-coded defaults — making the service straightforward to configure in containerised deployments.

Communication Patterns

Asynchronous Messaging (primary)

ZavaQueueBridge publishes messages to RabbitMQ over AMQP 0-9-1 using RabbitMQ.Client 5.2.0. A new IConnection / IModel (channel) pair is created per poll cycle batch and disposed after the batch completes. Messages are marked persistent (IBasicProperties.Persistent = true) to survive broker restarts.

  • Exchange: filedrop.events — Topic, durable, non-auto-delete
  • Dead-letter exchange: zava.dlx — Fanout, durable, non-auto-delete
  • Routing key strategy: derived at runtime from the source file extension (filedrop.<ext>)

Resilience

No circuit-breaker, retry, or timeout policies are implemented in the application code. Connection failures during a poll cycle propagate as exceptions that are caught and logged at the top-level loop; the worker continues to the next poll interval. There is no exponential back-off or jitter.

AutomaticRecoveryEnabled is explicitly set to false on the ConnectionFactory, meaning any broker disconnection requires a manual restart of the service.

Service Discovery

No service discovery mechanism is used. The RabbitMQ host, port, virtual host, username, and password are resolved from environment variables (primary) or app.config appSettings (fallback), then default to the hard-coded values rabbitmq:5672 /zavabank.

Startup Dependency Chain

The service starts immediately on launch. It does not wait for RabbitMQ to become available before entering the polling loop. A connection attempt is made on the first batch that contains files; a failure at that point will be logged and retried on the next poll interval.

Security Posture

  • Transport security: No TLS configured. AMQP traffic is sent in plain text on port 5672. There is no option in the current code to use AMQP over TLS (port 5671).
  • Authentication: Username/password credentials are passed to RabbitMQ via ConnectionFactory.UserName / ConnectionFactory.Password. Credentials are sourced from environment variables or app.config; they are not encrypted at rest.
  • Authorization: No application-level RBAC or claim-based checks. Access control is delegated entirely to RabbitMQ broker permissions.
  • HTTP authentication/TLS: Not applicable — no HTTP surface is exposed.

Primary Workflows

Workflow 1: File Detection & Queuing

Trigger: A file is created, modified, or renamed in the drop directory.

Steps:

  1. FileSystemWatcher raises a Created, Changed, or Renamed event.
  2. The event handler calls QueuePendingFile, which validates the file is a candidate (.csv, .txt, .dat extension; not named processed or error).
  3. If valid, the file path is added to the thread-safe PendingFiles set.
  4. The file will be included in the next poll-cycle batch.

Business Rule: Only files with .csv, .txt, or .dat extensions are eligible for processing. Files named processed or error (subdirectory markers) are silently ignored.

Workflow 2: Poll-Cycle File Processing

Trigger: The poll loop fires every 5 seconds (configurable via WORKER_POLL_INTERVAL_MS).

Steps:

  1. Scan the drop directory with Directory.GetFiles to catch any files missed by the watcher (e.g., files present before startup).
  2. Queue all discovered files through the same candidate filter.
  3. Drain the PendingFiles set atomically into a processing batch.
  4. If the batch is empty, log "No files available" and wait for the next interval.
  5. Open a single RabbitMQ connection and channel for the entire batch.
  6. For each file in the batch, execute the Single File Processing sub-workflow (Workflow 3).
  7. Close the connection and channel after the batch completes.

Workflow 3: Single File Processing

Trigger: Called per-file within a poll-cycle batch.

Steps:

  1. Guard checks: Skip if the file no longer exists (deleted before processing) or if the path falls under the processed/ or error/ subdirectory.
  2. Wait for file readiness: Attempt to open the file for reading up to 5 times with 250 ms back-off to handle partially-written files.
  3. Parse records: Dispatch to CSV parser (header-row field names) or fixed-width parser (positional field extraction) based on file extension.
  4. Raise InvalidOperationException if the file is empty.
  5. Publish messages: For each parsed record, build a JSON envelope and publish to filedrop.events with routing key filedrop.<ext>. Messages are marked persistent.
  6. Archive success: Move the file to the processed/ directory. If a file with the same name already exists, prepend a yyyyMMddHHmmss timestamp to the destination file name.
  7. On error: Publish a dead-letter message to zava.dlx, then move the file to the error/ directory.

Workflow 4: Dead-Letter Handling

Trigger: An unhandled exception during Single File Processing.

Steps:

  1. Build a dead-letter JSON envelope (sourceFile, error, failedAt).
  2. Publish to the zava.dlx fanout exchange with an empty routing key.
  3. Move the source file to the error/ subdirectory.
  4. Log the failure to stdout.

Downstream consumers subscribed to queues bound to zava.dlx are responsible for alerting, reprocessing, or discarding failed files.

Cross-Service Data Flows

ZavaQueueBridge operates as a pure producer in a unidirectional pipeline. There is no request-response, no callback, and no data read back from downstream consumers.

Data flow:


Upstream Producer  -->  /shared/filedrop  -->  ZavaQueueBridge  -->  filedrop.events (RabbitMQ)
                                                        |
                                                        +--> zava.dlx (on failure)
  • Upstream file producers (not part of this codebase) are responsible for generating correctly-formatted CSV or fixed-width files and placing them in the drop directory.
  • Downstream consumers (not part of this codebase) subscribe to queues bound to filedrop.events and process individual record messages. They are the source of truth for record persistence.
  • Dead-letter consumers (not part of this codebase) subscribe to zava.dlx and handle failed-file notifications.

There is no circuit-breaker fallback that preserves partial business outcomes — a RabbitMQ connection failure causes the entire poll-cycle batch to fail; files remain in the drop directory and will be retried on the next poll interval.

Business Rules & Decision Logic

File Eligibility Rules

  • Accepted extensions: Only .csv, .txt, and .dat files are processed. All other extensions are silently ignored.
  • Excluded names: Files or directories named processed or error are excluded regardless of extension, preventing recursive processing of archived files.
  • Empty file rejection: A file with zero lines raises an InvalidOperationException and is sent to the dead-letter flow.

File Readiness Rule

  • A file is retried up to 5 times with 250 ms intervals before being considered readable. This accommodates files being written by the upstream producer when the watcher fires prematurely. No explicit failure is raised if the file is never readable — the exception from File.Open propagates and triggers the dead-letter flow.

Parsing Rules

  • CSV: The first line is always the header row; subsequent non-blank lines are data rows. Values are comma-delimited with basic quote handling (characters between " are treated as a single token regardless of commas within). Leading and trailing whitespace is trimmed from each field value.
  • Fixed-width: Lines are padded to 80 characters. Five fixed fields are extracted by byte position: RecordType (0–9), CustomerId (10–29), AccountId (30–49), Amount (50–64), Details (65–79). Values are trimmed of whitespace.

Routing Rule

  • The RabbitMQ routing key is filedrop.<ext> where <ext> is the lower-cased file extension without the leading dot (e.g., filedrop.csv). If the extension is absent, the key filedrop.unknown is used.

Archive Collision Rule

  • If a file with the same name already exists in the processed/ or error/ directory, the destination file name is prefixed with a yyyyMMddHHmmss timestamp (derived from DateTime.Now at the moment of the move).

Error Handling

  • Per-file errors are caught at the batch loop level: a failing file publishes a dead-letter message and is moved to error/; the remaining files in the batch continue to be processed.
  • Poll-cycle errors (e.g., RabbitMQ connection failure) are caught at the top-level loop: the exception is logged to stdout and the worker waits for the next poll interval. No exponential back-off or alerting is implemented.
  • Graceful shutdown: On Ctrl+C or SIGTERM, _keepRunning is set to false; the current file in progress finishes, the batch loop exits cleanly, and the FileSystemWatcher is disposed.

Audit & Logging

  • All significant events are written to stdout (console): startup configuration, per-file publish counts, file move confirmations, and error messages. No structured logging, log levels, or log aggregation framework is used.
  • The file-system archive directories (processed/, error/) serve as a durable audit trail; no TTL or cleanup policy is applied by this service.

Authorization

No business-level authorization is enforced. Any process or container with access to the drop directory can place files for processing, and any RabbitMQ user with publish permissions on the configured exchanges can receive messages.

Version & Compatibility Risks

RabbitMQ.Client 5.2.0 was released in 2019 and targets the AMQP 0-9-1 protocol with a synchronous API surface. The current stable release line is 6.x/7.x, which introduces async-first APIs, IConnection.CreateModel() deprecation in favour of IChannel, and improved connection-recovery semantics. Migrating to a modern runtime (e.g. .NET 8 or .NET 10) would require upgrading the client to at least 6.x.

The use of System.Web.Script.Serialization.JavaScriptSerializer (from System.Web.Extensions) is a .NET Framework-only API. It is not available on .NET Core / .NET 5+. Any migration to a modern runtime must replace it with System.Text.Json or Newtonsoft.Json.

.NET Framework 4.8 itself is in long-term maintenance mode and receives only security fixes. Microsoft's guidance for new workloads is .NET 8 LTS or .NET 10.

Notable Observations

  • Single external dependency: The application has an extremely lean dependency footprint — only one NuGet package — which makes a runtime migration straightforward once the .NET Framework-specific APIs are addressed.
  • System.Web.Extensions coupling: The reliance on JavaScriptSerializer from System.Web.Extensions is the primary source-code migration blocker; it is not available outside .NET Framework and the assembly is flagged by AppCAT.
  • RabbitMQ.Client net451 target in use: The hint path in the .csproj points to the net451 library folder of the NuGet package, which works fine on .NET 4.8 but confirms the dependency was never updated since its original install.
  • No version pinning via NuGet lock file or Directory.Packages.props: Dependency versions are fixed only in packages.config; adding a packages.lock.json or migrating to SDK-style PackageReference with a lock file would improve reproducibility.

Data Architecture & Persistence Layer

ZavaQueueBridge has no relational database or ORM layer; its only persistent data stores are the local file system (drop, processed, and error directories) and the RabbitMQ broker to which it publishes durable messages.

Caching Strategy

No caching layer is implemented. All file content is read directly from disk on every processing attempt; there is no in-memory query cache, result cache, or distributed cache.

Data Ownership Boundaries

The application is a single-process, single-service worker. There is no multi-service data sharing, CQRS split, or read/write separation to document.

Data flow boundaries:

  • Inbound: Files written by external producers to /shared/filedrop (a shared volume in containerised deployments). ZavaQueueBridge only reads from this location and does not own the file creation process.
  • Processing state: The pending-file set (HashSet<string> PendingFiles) is held in-process memory and is not persisted. A process restart will reprocess any files that remain in the drop directory on the next poll cycle.
  • Outbound: Parsed records are published as durable AMQP messages to RabbitMQ. Downstream consumers (not part of this repository) are responsible for consuming and persisting those records.
  • Audit trail: Successfully processed files are moved to processed/; failed files are moved to error/ with a timestamp prefix. These directories serve as a simple file-based audit trail with no TTL or cleanup policy.

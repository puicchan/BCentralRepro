Data Storage & External Services

The service uses a single SQL Server database accessed directly through JDBC for alert, transaction, account, rule, and session-user lookups. It also calls an external authentication gateway WhoAmI endpoint to resolve session tokens from SSO cookie values when request headers do not contain explicit tokens.

Key Architectural Decisions

  • Uses Struts interceptor-based authentication (AuthTokenInterceptor) to protect all actions except login and health.
  • Uses direct SQL via PreparedStatement instead of ORM, keeping query logic close to each action.
  • Uses a fallback identity resolution flow from SSO cookie to external WhoAmI service for mixed Java/.NET authentication compatibility.

The API contract is modeled with action form properties and response records: FraudAlertRecord, FraudRuleRecord, and SessionUser are service-level models used to render views and maintain authenticated identity. Communication Patterns

Communication is synchronous throughout: browser-to-service HTTP, service-to-SQL Server JDBC calls, and optional service-to-auth-gateway HTTP call for SSO token resolution. No asynchronous messaging or event bus usage was found. Service discovery is URL-based via configuration (auth.gateway.whoami.url) rather than logical registry. Security posture is session-token based with a custom Struts interceptor and optional bearer/header/cookie token extraction; no explicit TLS enforcement or framework-level authorization annotations were found in this codebase.

Primary Workflows

Workflow 1: Analyst reviews flagged transaction queue

  1. Analyst opens flagged queue.
  2. Authentication interceptor validates analyst session token.
  3. System loads latest New/InReview alerts with account and amount context.
  4. Analyst opens transaction detail for one alert and reviews severity and description.

Business rules involved: only active authenticated users can access queue; queue focuses on unresolved statuses (New, InReview).

Workflow 2: Analyst makes alert decision

  1. Analyst submits approve/reject decision and optional notes for a selected alert.
  2. System validates required inputs (alertId, non-empty decision).
  3. Alert status is transitioned to Approved or Rejected.
  4. Resolution notes are augmented with current analyst username and persisted.

Business rules involved: decision determines final status; actor attribution is appended to resolution notes.

Workflow 3: Fraud administrator maintains rule catalog

  1. Admin views current rule list.
  2. Admin opens rule form for create or edit.
  3. System validates required fields (ruleName, severity) and numeric formats (threshold/time window).
  4. System inserts or updates rule record, or deletes selected rule.

Business rules involved: rule metadata must pass validation before persistence.

Cross-Service Data Flows

The main cross-service composition occurs during authentication fallback. If local token lookup fails, the app sends the SSO cookie to the auth-gateway WhoAmI endpoint, receives a session token, and retries user resolution in SQL. For business data, fraud alerts are combined with account and transaction context through SQL joins in one read path. If identity bridge resolution fails, the user is redirected to login, resulting in a degraded but safe business outcome (no unauthorized fraud operations access).

Business Rules & Decision Logic

  • Access control rule: protected workflows require authenticated active user session.
  • Queue inclusion rule: only alerts in New or InReview status are listed for triage.
  • Decision rule: approval and rejection map to explicit terminal statuses and persist audit-style note attribution.
  • Rule management validation: rule name and severity are mandatory; threshold and time-window values must parse as numeric.
  • Transaction handling model: each action manages its own DB operation boundaries; failures surface user-facing action errors without partial in-memory state transition.

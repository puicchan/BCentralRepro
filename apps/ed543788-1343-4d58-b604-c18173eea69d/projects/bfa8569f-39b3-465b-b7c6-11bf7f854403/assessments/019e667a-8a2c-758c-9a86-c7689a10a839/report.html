Data Storage & External Services

The application uses a single SQL Server database (ZavaBankDB) through ADO.NET for loan product lookup and loan application persistence. It also integrates with external endpoints for centralized authentication (AuthGatewayLoginUrl, AuthGatewayLogoutUrl) and loan submission (LoanOriginationApiUrl). No cache, message broker, or secondary datastore is defined in this repository.

Key Architectural Decisions

  • Uses ASP.NET Web Forms code-behind pages rather than MVC-style controllers.
  • Uses direct SQL commands (ADO.NET) instead of an ORM/repository abstraction.
  • Uses redirect-based delegated authentication with an external auth gateway and local forms auth cookie.

DTOs & Contracts

The application does not define explicit DTO classes; contract data is exchanged using Web Forms controls and inline XML payload generation. Request contract to the external loan origination API is an XML document with elements customerId, loanProductId, requestedAmount, and termMonths. Response contract from that API is not strongly typed in this codebase and is treated as generic response content. For persistence model details and table-level data definitions, see data-architecture.md.

Communication Patterns

Synchronous patterns dominate this codebase: browser-to-WebForms page requests and portal-to-external API HTTP POST calls. No asynchronous messaging, queue usage, or event choreography is present. There is no circuit breaker, retry, timeout policy configuration, or service discovery mechanism in code/config; outbound URLs are statically configured in web.config. API availability depends on both the auth gateway endpoints and loan origination endpoint being reachable. Security posture at the API layer is forms-auth cookie gating for portal pages, with no explicit TLS enforcement or token-based service-to-service auth in repository code.

Core Business Workflows

The application supports customer-facing loan submission workflows through a guided UI and integrates with external authentication and loan-origination services. Core business behavior centers on validation, submission, and status visibility for recent applications.

Primary Workflows

Workflow 1: User Authenticates and Enters Portal

  1. User requests the portal entry page.
  2. Portal verifies authentication state.
  3. If unauthenticated, portal redirects to login page and then to auth gateway with return URL.
  4. User completes authentication and returns to portal.
  5. Portal loads product list and recent application history.

Workflow 2: Submit Loan Application

  1. User completes wizard steps for customer and loan details.
  2. Portal validates amount and term values before advancing to final step.
  3. Portal builds review summary and on finish creates loan application payload.
  4. Portal sends payload to loan origination API.
  5. Portal records submitted application in SQL Server with status Submitted.
  6. Portal refreshes loan history and confirms submission to user.

Cross-Service Data Flows

The workflow is orchestrated by ZavaLoanPortal. Authentication data flow depends on redirects to ZavaAuthGateway and return to the portal. During submission, the portal synchronously sends the application payload to the Loan Origination API and separately persists the application row to SQL Server. If the external loan API call fails, the current implementation swallows exceptions and continues local flow, which can produce a business-visible partial-success state where local history shows submission while external processing outcome is uncertain.

Business Rules & Decision Logic

  • Access control rule: unauthenticated users are redirected to login/auth gateway before portal usage.
  • Validation rule: requested amount and term must parse to numeric values before finishing wizard submission.
  • Decision logic: final submission triggers two actions (external API call and local DB persistence) in sequence.
  • State transition: application is written locally with status Submitted on completion.
  • Error-handling behavior: outbound API errors are caught and ignored, so user-facing success can still occur when external integration fails.
  • Authorization model: forms-authenticated users can access portal pages; login/logout pages explicitly allow anonymous access.

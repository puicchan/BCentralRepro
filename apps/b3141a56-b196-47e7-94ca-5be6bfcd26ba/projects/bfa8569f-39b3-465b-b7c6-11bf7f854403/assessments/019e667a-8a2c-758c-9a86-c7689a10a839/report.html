Data Storage & External Services

The service persists and reads operational alert data from SQL Server using direct SQL statements against transaction, rule, and alert history tables. It integrates with RabbitMQ by calling the management HTTP API to publish alert payloads to the zava.notifications exchange.

Key Architectural Decisions

  • Uses direct SQL and explicit transaction scopes in service methods instead of an ORM layer.
  • Keeps health probing isolated in a lightweight IHttpHandler endpoint.
  • Decouples outbound notifications through RabbitMQ publish semantics so rule evaluation is not blocked on downstream consumers.

DTOs & Contracts

Service-level contract types are AlertRuleDefinition, AlertRuleInfo, AlertRulesResponse, AlertEvaluationResponse, and AlertRuleMutationResponse, all exposed as WCF DataContract classes with mutable properties. Internal-only transport type AlertEvent is used for outbound messaging and is serialized with JavaScriptSerializer before publishing. No OpenAPI, protobuf, or GraphQL schema files were detected.

Communication Patterns

Inbound communication is synchronous SOAP over basicHttpBinding, with immediate response or FaultException for validation and missing-resource failures. Internally, business logic performs synchronous SQL operations through ADO.NET and then posts alert events synchronously over HTTP to the RabbitMQ management API; downstream consumption is asynchronous after publish. No circuit breaker, retry policy, service discovery, or API gateway logic is implemented in this codebase. Security posture is minimal: no authentication or authorization checks are configured at the API layer and transport is HTTP unless externally terminated.

Core Business Workflows

This service supports account alerting by evaluating financial transactions against configured alert rules and emitting notifications. It also supports configuration and maintenance of account-specific rule assignments.

Primary Workflows

Workflow 1: Evaluate transaction and trigger notifications

  1. A client invokes EvaluateTransaction with a transaction identifier.
  2. The service loads transaction/account context and enabled rules for that account.
  3. Rule decision logic evaluates thresholds and behavioral patterns (LOW_BAL, LARGE_TXN, OVERDRAFT, INTL_WIRE, DAILY_SPEND).
  4. For each match, the service emits an alert event and records a history entry including whether publication succeeded.
  5. The service returns triggered rule codes and publication summary to the caller.

Workflow 2: Manage alert rule configuration

  1. A client invokes CreateAlertRule or UpdateAlertRule with rule metadata and account targeting information.
  2. Input validation ensures rule identity and required account/customer context.
  3. The service executes transactional SQL updates to keep master rule data and account mapping consistent.
  4. A mutation response returns success state with identifiers for created or updated entities.

Cross-Service Data Flows

The service has one outbound cross-system composition path: after transaction rule evaluation, it serializes an internal alert event and publishes to RabbitMQ for downstream notification services. Business degradation behavior is explicit: when publish fails, workflow still commits alert history with NotificationSent false and returns a successful evaluation response containing local trigger results.

Business Rules & Decision Logic

  • Validation rules: transactionId, accountId, ruleId, and rule naming fields are validated and invalid input returns SOAP faults.
  • Decision logic: rule code switches map to threshold and behavior checks, including daily spend aggregate calculation.
  • State transitions: account alert configuration transitions through create and update operations with modified timestamps.
  • Data integrity rules: create and update operations are wrapped in SQL transactions to maintain rule and account mapping consistency.
  • Error handling: missing transaction or rule resources produce faults; notification publish failures are tolerated and audited.
  • Authorization: no role-based authorization checks are defined at service operation level in this repository.

Data Storage & External Services

The application uses a single Microsoft SQL Server database (ZavaBankDB) accessed via JDBC. It reads from and writes to the Accounts, AccountTypes, and InterestAccruals tables. The InterestAccruals table is created by InterestBootstrapServlet at startup if it does not exist. No external services, caches, message brokers, or third-party APIs are used; all data access is direct SQL via the mssql-jdbc driver.

Key Architectural Decisions

  • Plain Servlet architecture: The application uses raw javax.servlet.HttpServlet subclasses without a higher-level framework (no Spring, Jakarta EE CDI, or JAX-RS), keeping the dependency footprint minimal.
  • Configuration via environment variables with properties fallback: InterestConfig reads database credentials and defaults from environment variables first, falling back to interest.properties, which supports both container-based deployments and local development.
  • Transactional batch accrual: InterestAccrueAllServlet processes all active accounts in a single JDBC transaction with explicit commit/rollback, ensuring atomic batch interest accrual.

DTOs & Contracts

There are no DTO or contract classes. All request parsing and response serialization are performed inline within each servlet using org.json.JSONObject:

  • Request parsing: InterestCalculateServlet and InterestAccrueAllServlet read the raw HTTP body as a string and parse it manually with new JSONObject(body), using optInt, optString, optDouble, and optBoolean accessors with inline defaults.
  • Response serialization: Responses are constructed by manually setting keys on a JSONObject instance and writing its string representation to the HttpServletResponse writer.
  • Error responses: Error payloads are written as raw JSON string literals (e.g., "{\"status\":\"ERROR\",\"message\":\"...\"}") rather than through a shared model.
  • No OpenAPI / Swagger specification, no protobuf schemas, and no GraphQL schemas exist.
  • No immutable request/response models are defined; field structure is implicit in each servlet's implementation.

For the data fields accessed from the database, see data-architecture.md.

Communication Patterns

Synchronous only. All communication is direct HTTP between an external client and the Tomcat-hosted servlet. There is no inter-service communication, no message broker, and no event-driven integration.

  • Service discovery: None. The application is reached directly by hostname/IP and port 8080; no service registry (Eureka, Consul, Kubernetes DNS) is configured.

  • Resilience patterns: None. No circuit breaker (Resilience4j, Hystrix, Polly), no retry policy, no timeout configuration, and no bulkhead pattern are implemented.

As a result, API availability depends on the SQL Server being accessible at application startup.
  • Security posture: No authentication, authorization, or TLS is configured at the API level. All endpoints — including /api/interest/calculate, /api/interest/accrue-all, and /internal/bootstrap — are publicly accessible with no credentials, tokens, or role checks required. Core Business Workflows

ZavaInterestCalculator is an interest calculation engine for Zava Bank that computes and optionally applies simple, compound, or amortized interest charges to customer accounts, and supports bulk interest accrual across all active accounts in a single atomic operation.

This is a single-service application. No cross-service communication exists. Accounts and AccountTypes are treated as externally managed tables (no DDL ownership); the application reads them but does not create or maintain their schema.

Primary Workflows

Workflow 1: Calculate Interest for a Single Account

A caller POSTs to /api/interest/calculate with an account ID, interest type, and calculation parameters. The application:

  1. Parses and validates the JSON request body; returns HTTP 400 if the body is invalid JSON or accountId is missing/zero.
  2. Loads the account's current balance and account-type interest rate from the database; returns HTTP 404 if the account does not exist.
  3. Applies defaults for any omitted parameters: interestType defaults to simple, days to 30, annualRate to the account-type rate (or the configured default if the rate is zero), compoundsPerYear to 12, and termMonths to 12.
  4. Computes the interest amount using the selected formula (see Business Rules below).
  5. If applyToBalance is true, executes a transactional write: updates the account balance and inserts an InterestAccrual audit record. If the database write fails, the transaction is rolled back and HTTP 500 is returned.
  6. Returns the calculation result regardless of whether it was applied.

Workflow 2: Batch Accrue Interest for All Active Accounts

A caller POSTs to /api/interest/accrue-all (typically from a scheduled job or administrator). The application:

  1. Parses optional parameters; uses defaults if omitted or if the body is absent.
  2. Opens a single database connection with autoCommit=false.
  3. Queries all accounts with Status = 'Active', joining AccountTypes for per-type default rates.
  4. For each active account: computes interest using the selected formula, then batches an UPDATE Accounts and an INSERT INTO InterestAccruals statement.
  5. Commits the transaction after all accounts are processed. If any SQL error occurs, the entire batch is rolled back (all-or-nothing semantics).
  6. Returns a summary: count of accrued accounts and total interest accrued.

Workflow 3: Application Bootstrap (Schema Initialization)

On WAR deployment, before any HTTP traffic is served, InterestBootstrapServlet (load-on-startup order 1) runs once:

  1. Opens a JDBC connection to SQL Server.
  2. Executes an idempotent DDL statement: IF OBJECT_ID('InterestAccruals','U') IS NULL CREATE TABLE InterestAccruals (...).
  3. If the database is unavailable or the DDL fails, a ServletException is thrown, which causes Tomcat to abort deployment — the entire application becomes unavailable until the issue is resolved and the container is restarted.

Cross-Service Data Flows

This is a single-service application with no inter-service communication. All data originates from and is persisted to a single SQL Server database. There are no aggregation patterns, no circuit breakers, and no fallback behaviors involving downstream services.

The only external dependency is the SQL Server database. If the database becomes unavailable mid-request, the relevant servlet returns HTTP 500 with {"status":"ERROR"}. No retry or circuit-breaker logic is implemented.

Business Rules & Decision Logic

Interest Calculation Formulas

Interest TypeFormulaKey Parameters
simpleP × r × d / 365principal (P), annual rate (r), days (d)
compoundP × ((1 + r/n)^(n × d/365) − 1)principal (P), annual rate (r), compounds per year (n), days (d)
amortizedDerived monthly payment minus monthly principal component, prorated by daysprincipal (P), annual rate (r), term months, days (d)

An unsupported interestType value throws an IllegalArgumentException, returning HTTP 400.

Parameter Defaults & Guards

  • days ≤ 0 → reset to 30
  • annualRate ≤ 0 (or not supplied) → use account-type rate; if account-type rate is also ≤ 0, use configured default (0.015 / 1.5%)
  • compoundsPerYear ≤ 0 → reset to 12
  • termMonths ≤ 0 → reset to 12
  • principal ≤ 0 → return zero interest (no calculation performed)

Batch Accrual Scope

Only accounts with Status = 'Active' are included in batch accrual. Inactive, closed, or frozen accounts are excluded.

Transaction Boundaries

  • Single-account accrual (applyToBalance=true): one JDBC transaction covering one UPDATE Accounts + one INSERT INTO InterestAccruals. Failure rolls back both.
  • Batch accrual (/api/interest/accrue-all): one JDBC transaction covering all active accounts. A failure on any account rolls back the entire batch — no partial commits.

Error Handling

  • Invalid JSON → HTTP 400
  • Missing/invalid accountId → HTTP 400
  • Account not found → HTTP 404
  • Unsupported interestType → HTTP 400 (via IllegalArgumentException)
  • Database error → HTTP 500 (internal message suppressed from response; only generic error returned to caller)

Audit Trail

Every successful application of interest (whether single-account or batch) writes an InterestAccrual record capturing: account ID, interest type, principal amount, annual rate, accrual days, interest amount, and timestamp. This provides a complete ledger of all interest events.

Authorization

No authentication or authorization is implemented. Any caller with network access to port 8080 may invoke any endpoint, including batch accrual and the bootstrap endpoint.

Version & Compatibility Risks

The javax.servlet:javax.servlet-api:3.1.0 dependency uses the legacy javax.servlet namespace, which was superseded by jakarta.servlet in Jakarta EE 9 (Servlet 5.0). Any migration to Tomcat 10+, WildFly 27+, or modern Jakarta EE containers would require a package rename across all source files. The org.json:json:20140107 artifact is over 12 years old; while functionally stable, it predates many security and API improvements and has known issues resolved in later versions. The mssql-jdbc:12.6.3.jre8 classifier locks the application to the Java 8 runtime; upgrading the JDK would require switching to the standard (non-jre8) artifact variant.

Notable Observations

  • Extremely minimal dependency footprint: With only 3 declared dependencies the application is lightweight, but this comes at the cost of hand-rolling concerns such as JSON serialization, transaction management, and connection pooling that production-grade frameworks handle automatically.
  • No connection pooling library: The application opens and closes JDBC connections per request via DriverManager.getConnection() with no pooling (e.g., HikariCP, c3p0), which is a scalability concern under concurrent load.
  • org.json is over 12 years old: Version 20140107 predates substantial API changes; upgrading to a current release or replacing with Jackson/Gson is advisable before cloud migration.
  • No logging framework declared: The application does not declare SLF4J, Log4j, or any logging library, meaning log output relies on Tomcat's default java.util.logging, with no structured or configurable logging for cloud observability.

Data Ownership Boundaries

The application uses a single shared SQL Server database (ZavaBankDB). There is no database-per-service separation and no logical schema partitioning.

  • There are no cross-service data access patterns; there is no inter-service communication whatsoever. All data access is direct JDBC within a single JVM process.
